## 项目依赖

### 示例

```json
{
  "name": "pnpm-demo",
  "version": "1.0.0",
  "dependencies": {
    "alfred-color-converter": "^0.0.11"
  }
}
```

- 项目 `pnpm-demo` 依赖 `alfred-color-converter`
- `alfred-color-converter` 依赖 `color-convert`
- `color-convert` 依赖 `color-name`

在此示例，项目直接依赖为 `alfred-color-converter`，间接依赖有 `color-convert` 和 `color-name`。

### 依赖目录

- `node_modules/` 仅存放项目**直接依赖**
- `node_modules/.pnpm/` 该目录下的包是项目目录下唯一“**真实**”的文件（指向全局 Store 文件）
- `node_modules/.pnpm/node_modules/` 默认情况下，项目所有**间接依赖**都会生成到该目录（类似于 npm/yarn 的扁平依赖结构），该目录下的包都是软链接（指向父级对应包）

### 完整目录结构

`tree -a`

```txt
node_modules
├── .pnpm
│   ├── alfred-color-converter@0.0.11
│   │   └── node_modules
│   │       ├── alfred-color-converter
│   │       └── color-convert -> ../../color-convert@2.0.1/node_modules/color-convert
│   ├── color-convert@2.0.1
│   │   └── node_modules
│   │       ├── color-convert
│   │       └── color-name -> ../../color-name@1.1.4/node_modules/color-name
│   ├── color-name@1.1.4
│   │   └── node_modules
│   │       └── color-name
│   └── node_modules
│       ├── color-convert -> ../color-convert@2.0.1/node_modules/color-convert
│       └── color-name -> ../color-name@1.1.4/node_modules/color-name
└── alfred-color-converter -> .pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter
```

> 无论依赖层级有多深，pnpm 构建的依赖目录层级最多到 `node_modules/.pnpm/node_modules/<package>` 这层，避免了扁平化 npm 之前目录层级过深导致的问题。

1. 这种目录结构完全兼容 Node.js 的模块解析算法
2. 只有显式声明的直接依赖才能在项目中访问，避免了幽灵依赖问题

### 依赖目录生成过程

1. 将直接和间接依赖生成到 `node_modules/.pnpm` 目录下
    - `alfred-color-converter@0.0.11`
    - `color-convert@2.0.1`
    - `color-name@1.1.4`

```txt
node_modules
└── .pnpm
    ├── alfred-color-converter@0.0.11 🆕
    │   └── node_modules
    │       └── alfred-color-converter
    ├── color-convert@2.0.1 🆕
    │   └── node_modules
    │       └── color-convert
    └── color-name@1.1.4 🆕
        └── node_modules
            └── color-name
```

> 观察发现，`alfred-color-converter@0.0.11` 与 `alfred-color-converter` 之间夹了一层 `node_modules`，目的是：
>
> 1. 允许包导入本身。例如在 `alfred-color-converter` 内部调用 `require('alfred-color-converter/package.json')`，这个方式是允许的。[LOAD_PACKAGE_SELF](https://nodejs.org/api/modules.html#all-together)
> 2. 避免循环软链接。包的依赖会放在与依赖包相同的目录下。基于 Node.js 模块解析算法，依赖无论放在 `node_modules` 还是父级的 `node_modules` 作用都一样，Node.js 都能找到目标包。pnpm 这样设计目录结构是没有问题的。

> 我们知道 npm/yarn 扁平依赖结构下，若依赖版本有冲突且不兼容的情况下，会在子依赖项下创建 `node_modules`。而 pnpm 采用包名 + 版本号的目录形式，天然没有这种问题。

2. 通过软链接的方式关联依赖项
    - 将 `node_modules/.pnpm/color-convert@2.0.1/node_modules/color-convert` 链接到 `node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/color-convert`
    - 将 `node_modules/.pnpm/color-name@1.1.4/node_modules/color-name` 链接到 `node_modules/.pnpm/color-convert@2.0.1/node_modules/color-name`

```txt
node_modules
└── .pnpm
    ├── alfred-color-converter@0.0.11
    │   └── node_modules
    │       ├── alfred-color-converter
    │       └── color-convert -> ../../color-convert@2.0.1/node_modules/color-convert 🆕
    ├── color-convert@2.0.1
    │   └── node_modules
    │       ├── color-convert
    │       └── color-name -> ../../color-name@1.1.4/node_modules/color-name 🆕
    └── color-name@1.1.4
        └── node_modules
            └── color-name
```

3. 处理直接依赖
    - 将 `node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter` 链接到 `node_modules/alfred-color-converter`

```txt
node_modules
├── .pnpm
│   ├── alfred-color-converter@0.0.11
│   │   └── node_modules
│   │       ├── alfred-color-converter
│   │       └── color-convert -> ../../color-convert@2.0.1/node_modules/color-convert
│   ├── color-convert@2.0.1
│   │   └── node_modules
│   │       ├── color-convert
│   │       └── color-name -> ../../color-name@1.1.4/node_modules/color-name
│   └── color-name@1.1.4
│       └── node_modules
│           └── color-name
└── alfred-color-converter -> .pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter 🆕
```

4. 将所有间接依赖及其依赖，提升到 `node_modules/.pnpm/node_modules/` 目录
    - 将 `node_modules/.pnpm/color-convert@2.0.1/node_modules/color-convert` 链接到 `node_modules/.pnpm/node_modules/color-convert`
    - 将 `node_modules/.pnpm/color-name@1.1.4/node_modules/color-name` 链接到 `node_modules/.pnpm/node_modules/color-name`

```txt
node_modules
├── .pnpm
│   ├── alfred-color-converter@0.0.11
│   │   └── node_modules
│   │       ├── alfred-color-converter
│   │       └── color-convert -> ../../color-convert@2.0.1/node_modules/color-convert
│   ├── color-convert@2.0.1
│   │   └── node_modules
│   │       ├── color-convert
│   │       └── color-name -> ../../color-name@1.1.4/node_modules/color-name
│   ├── color-name@1.1.4
│   │   └── node_modules
│   │       └── color-name
│   └── node_modules 🆕
│       ├── color-convert -> ../color-convert@2.0.1/node_modules/color-convert
│       └── color-name -> ../color-name@1.1.4/node_modules/color-name
└── alfred-color-converter -> .pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter
```

> 受扁平化 `node_modules` 结构的影响，npm 生态中很多包未正确使用依赖，其依赖项未在其 `package.json` 中列出。既然已成事实，为了最大限度地减少新用户遇到的问题，pnpm 默认将所有依赖项提升到 `node_modules/.pnpm/node_modules`。可通过 [hoist](https://pnpm.io/settings#hoist) 选项修改此特性。

### Node.js 模块解析

> By default, when Node.js loads a module from a path that is symbolically linked to a different on-disk location, Node.js will dereference the link and use the actual on-disk "real path" of the module as both an identifier and as a root path to locate other dependency modules. [--preserve-symlinks](https://nodejs.org/docs/v24.13.0/api/cli.html#--preserve-symlinks)

> 默认情况下，Node.js 遇到软链接会使用 `fs.realpathSync()` 获取其真正路径。[toRealPath](https://github.com/nodejs/node/blob/d14b484c73ff15010e51b0f290845306b0443d47/lib/internal/modules/cjs/loader.js#L767)

基于 pnpm 特殊的依赖结构，其依赖访问顺序如下：

1. 在项目 `index.js` 中访问 `require('alfred-color-converter')`
   根据 Node 模块解析算法，找到 `project/node_modules/alfred-color-converter`（软链接），Node 找到真正的目录位置 `project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter`，接着根据 `exports`、`main` 查找规则找到对应的文件。
2. 接着，`alfred-color-converter` 包内部（假设是 `dist/index.js`）访问了 `require('color-convert')`。注意，`require` 的解析起点是“当前模块的文件路径”，也就是 `project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter/dist/index.js`。因此 Node 最终解析到 `project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/color-convert`（软链接），Node 找到真正的目录位置 `project/node_modules/.pnpm/color-convert@2.0.1/node_modules/color-convert`。
3. 同理，在 `color-convert` 包内部（假设是 `dist/index.js`）访问 `require('color-name')`，Node 通过 `project/node_modules/.pnpm/color-convert@2.0.1/node_modules/color-name`（软链接）找到真正的文件 `project/node_modules/.pnpm/color-name@1.1.4/node_modules/color-name`。

伪代码：

```bash
# 在项目 index.js 访问 require('alfred-color-converter')
project/index.js
project/node_modules/alfred-color-converter
project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter

# 在 alfred-color-converter 的 dist/index.js 访问 require('color-convert')
project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/alfred-color-converter/dist/index.js
project/node_modules/.pnpm/alfred-color-converter@0.0.11/node_modules/color-convert
project/node_modules/.pnpm/color-convert@2.0.1/node_modules/color-convert

# 在 color-convert 的 dist/index.js 访问 require('color-name')
project/node_modules/.pnpm/color-convert@2.0.1/node_modules/color-convert/dist/index.js
project/node_modules/.pnpm/color-convert@2.0.1/node_modules/color-name
project/node_modules/.pnpm/color-name@1.1.4/node_modules/color-name
```

对于那些使用幽灵依赖的包（比如 `foo@1.0.0` 使用了 `bar@1.0.0`），由于 `bar` 未在 `foo` 的 `package.json` 列出，因此 pnpm 不会在 `project/node_modules/.pnpm/foo@1.0.0/node_modules` 目录创建 `bar` 包的软链接。此时，当在 `foo` 内部访问 `require('bar')` 时，基于 Node 的模块解析算法，会找到 `project/node_modules/.pnpm/node_modules` 这层（所有间接依赖都会在此目录下创建软链接），它找到 `project/node_modules/.pnpm/node_modules/foo`（软链接），进而访问 `project/node_modules/.pnpm/foo@1.0.0/node_modules/foo`。所以 pnpm 这种目录结构设计可以兼容到幽灵依赖的包。
